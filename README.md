# Campus Equipment Booking API — first version

TypeScript + Hono + local SQLite through D1. This folder originally contained only `exam_brief_en.md` and `rubric_en.md`; no instructor starter was present. The structure is deliberately small: `src/index.ts`, one SQL migration, and local Wrangler tooling. No Quality Gate review has been created.

## Install and run

Use Node.js 22 or newer and npm. From the project root:

```sh
npm ci
npm run db:migrate
npm run dev
```

Local Base API URL: **`http://localhost:8787/api`**. In a second terminal, start with:

```sh
curl -i http://localhost:8787/api/equipment
```

`db:migrate` creates the tables and seeds two equipment records. Repeating it applies only pending migrations. Local data persists in `.wrangler/state`; migrations and the dev server use the same default state location. Local development does not require a Cloudflare account. `wrangler.jsonc` configures the Worker and its DB binding for local development and deployment.

Type-check with `npm run typecheck`. If the binding configuration changes, run `npm run typegen` first. `worker-configuration.d.ts` is generated by Wrangler.

## Deploy to Cloudflare

Deployment requires a Cloudflare account authenticated through Wrangler:

```sh
npx wrangler login
npx wrangler whoami
```

For the first deployment, create a separate database for this API:

```sh
npx wrangler d1 create equipment-booking
```

This project's database has already been created and its UUID is recorded in `wrangler.jsonc`. Only run the create command when setting up a new database/account, then update `database_id` to the returned UUID. Do not use another project's database.

Then run:

```sh
npm run typegen
npm run typecheck
npm run db:migrate:remote
npm run deploy
```

`db:migrate:remote` creates the schema and seeds in Cloudflare D1; local SQLite data is separate and is not uploaded. For later code updates, apply any pending remote migrations and run `npm run deploy` again.

Public Base API URL for submission: **`https://campus-equipment-booking-api.thanhtike.workers.dev/api`**.

First public request:

```sh
curl -i https://campus-equipment-booking-api.thanhtike.workers.dev/api/equipment
```

Run the complete checks against the public API:

```sh
BASE_URL=https://campus-equipment-booking-api.thanhtike.workers.dev/api \
  bash scripts/curl_checks.sh
```

Cloudflare deployment completed on 2026-10-06. See `TEST_EVIDENCE.md` for actual public verification results.

## Simple curl examples

```sh
BASE_URL=http://localhost:8787/api
curl -i "$BASE_URL/bookings"
curl -i -X POST "$BASE_URL/bookings" \
  -H 'Content-Type: application/json' \
  -d '{"equipmentId":"eq-1","borrowerName":"Somchai Jaidee","startAt":"2026-10-20T09:00:00.000Z","endAt":"2026-10-20T11:00:00.000Z","purpose":"Class presentation"}'

# Copy the returned id into this variable:
BOOKING_ID=replace-with-returned-id
curl -i "$BASE_URL/bookings/$BOOKING_ID"
curl -i -X PATCH "$BASE_URL/bookings/$BOOKING_ID" \
  -H 'Content-Type: application/json' -d '{"purpose":"Updated presentation"}'
curl -i -X DELETE "$BASE_URL/bookings/$BOOKING_ID"
```

For a complete sequence including errors, run the curl commands in `scripts/curl_checks.sh` against the running API:

```sh
bash scripts/curl_checks.sh
# Optional: save your own actual results
bash scripts/curl_checks.sh | tee my-curl-results.txt
```

The script creates two bookings, checks expected statuses and JSON shapes, and deletes its bookings after the successful sequence. Run against a database without overlapping bookings on 2026-10-20 for `eq-1`. If interrupted or failed, bookings may remain; list and delete those before rerunning. Each response is printed so it can be inspected. See `TEST_EVIDENCE.md` for agent-executed checks; personal verification remains blank in `AI_LOG.md`.

## Code to explain

- `readInput` checks required strings, merges partial PATCH fields, normalizes timestamps, and validates the time order.
- `requireEquipment` checks the equipment ID with a bound SQL parameter.
- Two intervals overlap when `existing.startAt < requested.endAt` and `existing.endAt > requested.startAt`. Equal endpoints are allowed.
- INSERT/UPDATE include that condition in SQL; UPDATE adds `id <> ?` to avoid conflicting with itself.
- All request-derived SQL values use `.bind(...)`. DELETE uses `RETURNING id` to distinguish a missing booking from a successful deletion.

The full contract and simple ERD are in `API_CONTRACT.md`; the schema is in `migrations/0001_initial.sql`. These choices follow the exam contract, using the [D1 prepared statement API](https://developers.cloudflare.com/d1/worker-api/prepared-statements/) and [Hono's Workers integration](https://hono.dev/docs/getting-started/cloudflare-workers).
